= Module 4: Remediate the platform
:source-highlighter: rouge
:toc: macro
:toclevels: 2

With every model converted to RawDeployment, it's safe to start the platform work -but in the *right order*. Real clusters carry workloads the workshop has so far ignored: Ray clusters, TrustyAI services, AI Pipelines. Their data must be captured *before* you flip the components that host them, because some of those flips destroy state. Llama Stack is the one exception: its 2→3 transition has no compatible upgrade path (and Llama Stack is rebranded OGX in {target-version}), so the action is delete pre-upgrade and recreate fresh as an `OGXServer` post-upgrade (a configuration archive is available for reference only). This module starts with backups, deletes the LSDs, then runs the disables, then the {target-version} prerequisites, then operator uninstalls.

In this module you'll back up every workload whose data can be lost across the upgrade (Ray clusters, TrustyAI metrics, AI Pipelines), delete any LSDs so they can be recreated fresh in Module 7, update the `inferenceservice-config` ConfigMap with the hardware-profile ignorelist, flip the removed DSC components to `Removed`, tear down the Service Mesh v2 dependency, and finally uninstall the 2.x serving operators.

Order matters throughout. Back up RayClusters *before* disabling Ray. The `inferenceservice-config` ConfigMap must be updated *after* every ISVC is RawDeployment but *before* the disables, so the upgrade reconciler honours the new ignorelist. KServe Serverless must drain before you remove the Service Mesh v2 dependency. The Service Mesh member roll has to be deleted before its operator can be uninstalled.

== Learning objectives

By the end of this module, you'll be able to:

* Back up RayClusters, TrustyAI metrics + data, and AI Pipelines DSPAs ahead of destructive component changes, and delete any LlamaStackDistributions
* Update the `inferenceservice-config` ConfigMap with the hardware-profile ignorelist
* Flip the removed DSC components (`ray`, `codeflare`, `modelmeshserving`, `kserve.serving`) to `Removed`, and set `kueue` to `Removed` or `Unmanaged`
* Remove the Service Mesh v2 dependency including the lingering member roll, leaving the Maistra Istio CRDs for Module 7
* Uninstall the OpenShift Serverless, Service Mesh 2, and standalone Authorino operators

== Exercise 4.1: Back up the RayClusters

The `codeflare` operator is removed in {target-version}; KubeRay takes over Ray cluster management. Existing RayCluster CRs survive the controller swap, but back them up to disk first in case reconciliation drops fields.

[IMPORTANT]
====
Unlike the old 2.x helper script, the `raycluster.backup` action does *not* flip `codeflare` for you — and it *fails if CodeFlare is still `Managed`*. You must set `codeflare` to `Removed` in the DSC *manually, before* running the backup. Disabling CodeFlare is also a hard {target-version} upgrade prerequisite, required even if you have no RayClusters.

Do this only when you are ready to upgrade: CodeFlare provides essential security configuration for user-created RayClusters, so if you set it `Removed` and then delay the upgrade, users could create RayClusters while CodeFlare is absent.
====

Set `codeflare` to `Removed` first (Exercise 4.7 later re-applies this alongside `ray` — it's a no-op there because the field is already `Removed`):

[.console-input]
[source,role="execute"]
----
oc patch $(oc get dsc -o name | head -n1) --type=merge \
  -p '{"spec":{"components":{"codeflare":{"managementState":"Removed"}}}}'
----

The `raycluster.backup` action is non-destructive — it only reads and archives CR configuration. List the RayClusters to be captured, create the backup directory, then run the action from inside the rhai-cli pod:

[.console-input]
[source,role="execute"]
----
oc get rayclusters -A

oc exec -n rhai-migration rhai-cli-0 -- bash -c "
  mkdir -p /tmp/rhoai-upgrade-backup/ray_cluster
  rhai-cli migrate run --migration raycluster.backup --target-version 3.5.0 \
    --raycluster-output-dir /tmp/rhoai-upgrade-backup/ray_cluster
"

oc cp rhai-migration/rhai-cli-0:/tmp/rhoai-upgrade-backup/ray_cluster ./ray-backup
----

✓ `./ray-backup/` contains one YAML per RayCluster. `oc get rayclusters -A` still shows both clusters `ready`.

== Exercise 4.2: Back up TrustyAI metrics and data

TrustyAI's storage schema changed between 2.x and 3.x. Historical bias-detection metrics and training data can become unreadable without a pre-upgrade snapshot. Capture both before anything else touches the component.

Confirm TrustyAI is `Managed` (skip the rest of this exercise if not):

[.console-input]
[source,role="execute"]
----
oc get dsc default-dsc -o jsonpath='trustyai={.spec.components.trustyai.managementState}{"\n"}'
oc get trustyaiservice -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,STORAGE:.spec.storage.format'
----

In {target-version} both backups are single cluster-wide `rhai-cli migrate prepare` actions — they cover every namespace with a TrustyAIService in one pass, so there's no per-namespace loop. `trustyai.metrics` snapshots the scheduled metrics; `trustyai.data` archives data storage (auto-detecting PVC vs DATABASE from each TrustyAIService CR).

[IMPORTANT]
====
`--output-dir` is *required* when running inside the pod. The rhai-cli container root filesystem is read-only, so without an explicit `--output-dir` under the writable backup PVC the action fails with `permission denied`.
====

Run both actions from inside the rhai-cli pod:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- bash -c "
  # Metrics — cluster-wide snapshot to the backup PVC
  rhai-cli migrate prepare --migration trustyai.metrics --target-version 3.5.0 \
    --output-dir /tmp/rhoai-upgrade-backup/trustyai

  # Data — cluster-wide; auto-detects PVC vs DATABASE from each TrustyAIService CR
  rhai-cli migrate prepare --migration trustyai.data --target-version 3.5.0 \
    --output-dir /tmp/rhoai-upgrade-backup/trustyai
"
----

[NOTE]
====
These actions emit a benign `phase pre-upgrade but effective phase is post-upgrade` warning -ignore it. On a fresh lab the data backup may report an empty PVC for `test-trustyaiservice` (no bias-detection has been run, so there's no input data); the backup still completes successfully. `test-trustyaiservice-db` produces a SQL dump (the `-db` suffix marks it as database-backed).
====

Outside the pod, capture any `GuardrailsOrchestrator` `spec.otelExporter` blocks so you can restore them post-upgrade (no helper script for this either):

[.console-input]
[source,role="execute"]
----
oc get guardrailsorchestrator -A -o json \
  | jq -r '.items[] | select(.spec.otelExporter != null) | {ns: .metadata.namespace, name: .metadata.name, otelExporter: .spec.otelExporter}' \
  > /tmp/trustyai-guardrails-otel-backup-$(date +%Y%m%d%H%M).json
----

Copy the backup off the rhai-cli pod:

[.console-input]
[source,role="execute"]
----
oc cp rhai-migration/rhai-cli-0:/tmp/rhoai-upgrade-backup/trustyai ./trustyai-backup
----

=== Verify

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- ls -la /tmp/rhoai-upgrade-backup/trustyai
oc exec -n rhai-migration rhai-cli-0 -- find /tmp/rhoai-upgrade-backup/trustyai -maxdepth 2 -type f
----

[.console-output]
----
trustyai-metrics-test-trustyaiservice-20260218-175450.json
trustyai-metrics-test-trustyaiservice-db-20260218-175501.json
trustyai-data-test-trustyaiservice-20260218-175451/data/...
trustyai-db-test-trustyaiservice-db-20260218-175502/dump.sql
----

✓ The backup directory lists one `trustyai-metrics-<ns>-*.json` per namespace, plus a `trustyai-data-<ns>-*/` (PVC) tree for the PVC-backed service and a `trustyai-db-<ns>-*/dump.sql` for the database-backed one

== Exercise 4.3: AI Pipelines pre-upgrade check

DSPA pipelines themselves keep running across the upgrade, but the schema changed between 2.25 and {target-version} -deprecated fields (the old `instructLab` block) and any leftover `v1alpha1` DSPA CRs need detection. In {target-version} this is two rhai-cli actions: `ai-pipelines.pre-upgrade-check` scans for deprecated APIs and custom RBAC roles, and the `migrate prepare` variant of the same action snapshots every DSPA pod's health to disk (so the post-upgrade check can diff against it in Module 8).

First run the scan:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  rhai-cli migrate run --migration ai-pipelines.pre-upgrade-check --target-version 3.5.0
----

For this lab the check passes cleanly -nothing to remediate. On a production cluster it may report:

* *Warning: deprecated `instructLab` field* -safe to ignore; the field is tolerated during upgrade.
* *Deprecated v1alpha1 DSPA found* -run `rhai-cli migrate run --migration ai-pipelines.update-dsp-role --target-version 3.5.0` (or update each CR) to move to `v1`.
* *Custom RBAC roles that require updates* -consult the teams that use AI Pipelines, then run the `ai-pipelines.update-dsp-role` action. If the roles are GitOps/ArgoCD-managed, this is advisory; update the source.

Then capture the pre-upgrade baseline snapshot with the `migrate prepare` variant:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  rhai-cli migrate prepare --migration ai-pipelines.pre-upgrade-check --target-version 3.5.0
----

This writes `/tmp/rhoai-upgrade-backup/ai_pipelines/dspa_pre_upgrade_pods.json`.

[IMPORTANT]
====
This baseline file must *survive* the upgrade. It lives on the PVC mounted at `/tmp/rhoai-upgrade-backup` — *do not delete the PVC or the rhai-cli StatefulSet before the post-upgrade check runs in Module 7*, or the diff has nothing to compare against.
====

=== Verify

oc exec -n rhai-migration rhai-cli-0 -- ls /tmp/rhoai-upgrade-backup/ai_pipelines/dspa_pre_upgrade_pods.json
----

== Exercise 4.4: Delete any Llama Stack distributions

Llama Stack's 2→3 transition is "delete and replace." In {target-version}, Llama Stack is rebranded *OGX (Open GenAI Stack)* and the `LlamaStackDistribution` CR is replaced by *`OGXServer` (v1beta1)*. The schema also changed (SQLite → PostgreSQL, VectorDB API removed, Inference API became OpenAI-compatible), and there's no in-place data migration -so existing LSDs cannot be carried across. You'll recreate them as fresh `OGXServer` CRs in Module 7.

If no LSDs are present, this exercise is a no-op. If any exist, you can first archive their configuration for *reference only* (the SQLite databases cannot be imported into {target-version}'s PostgreSQL) with the `llamastack.backup` action -run it from inside the rhai-cli pod with an explicit `--output-dir`:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  rhai-cli migrate prepare --migration llamastack.backup --target-version 3.5.0 \
  --output-dir /tmp/rhoai-upgrade-backup/llamastack
----

Then delete every LSD so the upgrade has a clean slate and the `llamastackdistribution / config` blocker clears:

[.console-input]
[source,role="execute"]
----
oc get llamastackdistribution -A
oc get llamastackdistribution -A -o json \
  | jq -r '.items[]? | "\(.metadata.namespace) \(.metadata.name)"' \
  | while read NS NAME; do oc delete llamastackdistribution "$NAME" -n "$NS"; done
----

You'll deploy a fresh `OGXServer` (v1beta1) in Module 7, using the archive only as reference.

=== Verify

[.console-input]
[source,role="execute"]
----
oc get llamastackdistribution -A 2>&1 | tail -1
----

[.console-output]
----
No resources found
----

✓ All LSDs are deleted -the rhai-cli `llamastackdistribution / config` blocker is cleared

== Exercise 4.5: Update the inferenceservice-config ConfigMap

With every ISVC on RawDeployment (Module 3), apply the hardware-profile ignorelist changes to the `inferenceservice-config` ConfigMap. The `modelserving.hardwareprofiles-ignorelist` action does both jobs: adds `opendatahub.io/hardware-profile-name` and `opendatahub.io/hardware-profile-namespace` to the disallowed list (so the upgrade can migrate HardwareProfiles cleanly), and prevents InferenceService redeployment during the upgrade by marking the ConfigMap unmanaged (`opendatahub.io/managed=false`).

Back up first so you can restore the 2.x state if anything goes sideways:

[.console-input]
[source,role="execute"]
----
mkdir -p /tmp/rhoai-upgrade-backup
oc get configmap inferenceservice-config -n redhat-ods-applications -o yaml \
  > /tmp/rhoai-upgrade-backup/inferenceservice-config-backup.yaml
ls -lh /tmp/rhoai-upgrade-backup/inferenceservice-config-backup.yaml
----

Then run the action from inside the rhai-cli container:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  rhai-cli migrate run --migration modelserving.hardwareprofiles-ignorelist --target-version 3.5.0
----

=== Verify

[.console-input]
[source,role="execute"]
----
oc get configmap inferenceservice-config -n redhat-ods-applications \
  -o yaml | grep "hardware" -B 2 -A 2
oc get configmap inferenceservice-config -n redhat-ods-applications \
  -o jsonpath='managed={.metadata.annotations.opendatahub\.io/managed}{"\n"}'
----

✓ The ConfigMap lists `opendatahub.io/hardware-profile-name` and `opendatahub.io/hardware-profile-namespace` on the disallowed list, and `managed=false` so the upgrade reconciler honours the patch

[NOTE]
====
A side effect of `managed=false` is that the upgrade will *not* redeploy your model-serving pods. They keep running on the same kserve runtime image they were on. If you wanted a fresh runtime image post-upgrade (for example to pick up a newer vLLM build), restart each predictor explicitly after Module 7 once the platform is healthy.
====

== Exercise 4.6: Disable Kueue

Leaving Kueue `Managed` at upgrade time is the single highest-risk mistake -its admission webhook intercepts Job creation cluster-wide, and during the operator upgrade the webhook and its CRDs fall out of sync, which can reject Job submissions for *any* workload on the cluster. In {target-version}, `Managed` Kueue is *accepted by OLM but rejected at runtime*, so you must land on one of two supported end states before upgrading: *`Removed`* (disable Kueue entirely) or *`Unmanaged`* (hand Kueue to an externally installed Red Hat build of Kueue / RHBOK operator).

*Option A -Removed.* Disable Kueue entirely:

[.console-input]
[source,role="execute"]
----
oc patch $(oc get dsc -o name | head -n1) --type=merge -p '{
  "spec": { "components": { "kueue": { "managementState": "Removed" } } }
}'
----

✓ `oc patch` reports `patched` -`kueue.managementState` is now `Removed`. The `KueueReady` DSC condition flips to `False / reason=Removed`, which is expected (and it stays `False` after the upgrade -normal when Kueue is Removed).

*Option B -Unmanaged (external RHBOK).* Keep Kueue features via the external Red Hat build of Kueue. RHBOK must be installed and operational *first* (the `rhai-cli` RHBOK migration action can automate the move); then set the DSC component `Unmanaged`, optionally naming the default cluster/local queues:

[.console-input]
[source,role="execute"]
----
oc patch $(oc get dsc -o name | head -n1) --type=merge -p '{
  "spec": { "components": { "kueue": {
    "managementState": "Unmanaged",
    "defaultClusterQueueName": "default",
    "defaultLocalQueueName": "default"
  } } }
}'
----

[IMPORTANT]
====
Two caveats apply to the *Unmanaged* path:

* *Queue naming.* RHBOK reserves the name `default`, so rename any existing `LocalQueue` named `default` (e.g. to `rhoai-kueue-default`) before proceeding -otherwise admission breaks.
* *Namespace labels.* Label each Kueue-managed project `kueue.openshift.io/managed=true`. On a labeled namespace, these kinds must carry the `kueue.x-k8s.io/queue-name` annotation or admission is rejected: *pytorchjob, notebook, rayjob, raycluster, inferenceservice, llminferenceservice*.
====

== Exercise 4.10: Remove the Service Mesh dependency

OpenShift 4.19+ handles service mesh internally, so RHOAI 3.x no longer needs the embedded one:

[.console-input]
[source,role="execute"]
----
oc patch dsci default-dsci --type=merge -p '{
  "spec": { "serviceMesh": { "managementState": "Removed" } }
}'
----

Wait for the SMCP to drain, then delete the leftover ServiceMeshMemberRoll (the DSCI change drains the SMCP but leaves the SMMR with a `maistra.io/istio-operator` finalizer that only the still-installed Service Mesh operator can clear):

[.console-input]
[source,role="execute"]
----
until [ -z "$(oc get smcp -A --no-headers 2>/dev/null)" ]; do
  echo "Waiting for SMCP to drain..."
  sleep 5
done
oc delete smmr default -n istio-system --ignore-not-found
----

✓ Both the SMCP and SMMR are gone. The Service Mesh operator itself is uninstalled in Exercise 4.11.

== Exercise 4.11: Uninstall the 2.x serving operators

OpenShift Serverless, Service Mesh 2, and standalone Authorino were dependencies of the 2.x KServe Serverless stack. With that stack removed, uninstall them.

[.console-input]
[source,role="execute"]
----
# Delete the Subscription first, then the *source* CSV in the operator's install
# namespace. OLM auto-cleans the copies of a CSV that appear in every other
# namespace once the source is gone. Selecting by OLM's per-namespace label
# targets only the source, not any of the copies (deleting a copy just makes
# OLM re-sync it, leaving the operator installed).

# Standalone Authorino (installed in openshift-operators)
oc -n openshift-operators delete subscription authorino-operator --ignore-not-found
oc -n openshift-operators delete csv -l operators.coreos.com/authorino-operator.openshift-operators --ignore-not-found

# OpenShift Serverless (installed in openshift-serverless)
oc -n openshift-serverless delete subscription serverless-operator --ignore-not-found
oc -n openshift-serverless delete csv -l operators.coreos.com/serverless-operator.openshift-serverless --ignore-not-found

# Service Mesh 2 (installed in openshift-operators; safe now that the SMCP and SMMR are gone)
oc -n openshift-operators delete subscription servicemeshoperator --ignore-not-found
oc -n openshift-operators delete csv -l operators.coreos.com/servicemeshoperator.openshift-operators --ignore-not-found
----

[IMPORTANT]
====
Do *not* remove `servicemeshoperator3` (OSSM v3). Only the v2 operator (`servicemeshoperator`) is a leftover here. `servicemeshoperator3` is installed by the Cluster Ingress Operator to back the {target-version} *Gateway API* — it's a required part of the new platform, not a migration remnant.
====

[NOTE]
====
*Uninstalling the SM2 operator leaves its CRDs behind.* OLM operator uninstall never removes CRDs, so the Maistra `*.istio.io` CRDs (destinationrules, virtualservices, gateways, …) — all labelled `maistra-version` — survive here. After the upgrade, the OpenShift Gateway API "sail" controller refuses to install its own `networking.istio.io/v1` CRDs while these foreign ones exist (`"Istio CRDs are managed by an unknown party"`), which blocks the {target-version} *Data Science Gateway* and leaves the DSC `Not Ready`. Do *not* delete them now. They are cleaned up, with a 0-CR safety check, in *Module 7* — this is "Gap 2" in that module's post-upgrade gap report.
====

=== Verify

[.console-input]
[source,role="execute"]
----
oc get csv -A 2>/dev/null | grep -E 'authorino-operator\.|serverless-operator\.|servicemeshoperator\.' | grep -v rhods
echo "--- check complete ---"
----

[.console-output]
----
--- check complete ---
----

✓ No Serverless, Service Mesh 2, or standalone Authorino CSVs remain (the `\.` filter leaves OSSM v3 untouched). The leftover `maistra-version` Istio CRDs are expected — Module 7 removes them.

== Troubleshooting

*Issue*: `oc delete smmr` hangs.

*Solution*: The member roll's finalizer is processed by the Service Mesh 2 operator. Delete the SMMR *before* uninstalling the operator in Exercise 4.11. If you already uninstalled it, reinstall it briefly so the finalizer can process, then delete the SMMR.

*Issue*: A converted model goes `READY=False` during the Serverless teardown.

*Solution*: Check the predictor pod with `oc get pods -n <ns> -l serving.kserve.io/inferenceservice=<name>` and its logs. RawDeployment models do not depend on Knative, so the Serverless teardown itself shouldn't affect them; pod restarts later during the upgrade are expected (this is how they pick up the newer kserve and runtime images).

*Issue*: KServe Serverless teardown seems stuck.

*Solution*: It can take 5-10 minutes. Watch `oc get pods -n knative-serving` fall to zero. If it never drains, check `oc logs -n redhat-ods-applications -l app=kserve-controller-manager`.
