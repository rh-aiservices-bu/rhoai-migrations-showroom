= Migrating Red Hat OpenShift AI {source-version} to 3.5
:source-highlighter: rouge
:toc: macro
:toclevels: 2

toc::[]

Welcome to the Red Hat OpenShift AI migration workshop. You'll take a *production-shaped* OpenShift AI {source-version} cluster through an in-place migration to 3.5 -and unlike a clean demo cluster, this one has real workloads that don't survive a naive upgrade.

This is a *migration*, not a routine version bump. Moving from {source-version} to 3.x changes the routing layer (OpenShift Routes to Kubernetes Gateway API), the authentication model (oauth-proxy to kube-rbac-proxy), *removes* several components your workloads currently depend on -Serverless model serving, ModelMesh, and CodeFlare -and *replaces* the embedded Kueue with the external Red Hat build of Kueue (RHBOK). You can't just disable the removed components -you have to migrate the workloads off them first, in the right order, or you lose running models.

== Prerequisites

This workshop assumes you already have:

* *OpenShift administration skills* - you can work with the `oc` CLI, read and patch custom resources, and understand operators and OLM subscriptions
* *Familiarity with Red Hat OpenShift AI* - you know what a `DataScienceCluster` (DSC) and `DSCInitialization` (DSCI) are, what an `InferenceService` (ISVC) and `ServingRuntime` are, and roughly what the components do
* *Comfort reading and editing YAML* - several steps back up, edit, and recreate custom resources

*What this workshop does NOT cover*:

* Installing OpenShift AI 2.25 from scratch (your lab cluster already has it)
* Backup and restore (a real migration requires a verified backup first; that is out of scope here)
* Rolling back a failed migration

== Wait for the cluster to finish provisioning

[IMPORTANT]
====
*Do not start the workshop until every ArgoCD Application is `Synced` and `Healthy`.*

Your lab cluster is bootstrapped by OpenShift GitOps (ArgoCD), and a freshly provisioned cluster is often still reconciling its Applications for several minutes after you can first log in. If you begin before the bootstrap settles, workloads the early modules depend on (the ISVCs, the ModelMesh model, the workbenches) may not exist yet.

Run this *before* the next step -while auto-sync is still on, every Application should converge to `Synced`/`Healthy` on its own.
====

[NOTE]
====
*One Application is expected to stay `Progressing`: `rhoai-2254-operator-authorino`.* Its Subscription installs via *manual approval*, so it sits on a pending InstallPlan (which you approve later in the migration) and never reaches `Healthy` at this stage. The check below treats a `Progressing` `rhoai-2254-operator-authorino` as ready; every other Application must be `Synced`/`Healthy`.
====

The loop below polls every Application until they are all ready -`Synced`/`Healthy`, with the single authorino exception above -printing progress as it goes. It exits on its own once the cluster is ready (or after 20 minutes, whichever comes first).

[.console-input]
[source,role="execute"]
----
timeout=1200; interval=15; deadline=$(( $(date +%s) + timeout ))
# rhoai-2254-operator-authorino installs via manual approval and stays
# Progressing on a pending InstallPlan you approve later -treat it as ready.
expected=rhoai-2254-operator-authorino
while :; do
  states=$(oc get applications.argoproj.io -A \
    -o jsonpath='{range .items[*]}{.metadata.name}{" "}{.status.sync.status}{" "}{.status.health.status}{"\n"}{end}')
  total=$(printf '%s\n' "$states" | grep -c '[^[:space:]]' || true)
  ready=$(printf '%s\n' "$states" | awk -v want="$expected" '
    $2=="Synced" && $3=="Healthy" {c++; next}
    $1==want && $3=="Progressing" {c++; next}
    END {print c+0}')
  echo "$(date '+%H:%M:%S')  ${ready}/${total} Applications ready"
  if [ "$total" -gt 0 ] && [ "$ready" -eq "$total" ]; then
    echo "All Applications are ready -you're clear to start."; break
  fi
  if [ "$(date +%s)" -ge "$deadline" ]; then
    echo "Timed out after ${timeout}s with $(( total - ready )) Application(s) not ready."; break
  fi
  sleep "$interval"
done
----

=== Verify

List every Application with its sync and health status. Confirm all rows read `Synced` / `Healthy` -except `rhoai-2254-operator-authorino`, which is expected to read `Synced` / `Progressing` -before continuing:

[.console-input]
[source,role="execute"]
----
oc get applications.argoproj.io -A \
  -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,SYNC:.status.sync.status,HEALTH:.status.health.status'
----

If any *other* Application is stuck `OutOfSync`, `Progressing`, `Degraded`, or `Missing` after the loop times out, inspect it before proceeding:

[.console-input]
[source,role="execute"]
----
oc -n <namespace> describe application.argoproj.io <name>
----

== Disable ArgoCD auto-sync

[IMPORTANT]
====
*You cannot proceed with the workshop until this step is complete.*

The lab environment is bootstrapped with OpenShift GitOps (ArgoCD). Every `Application` ships with `syncPolicy.automated.selfHeal: true`, meaning ArgoCD will *revert* any change you make on the cluster back to what its Git source says within seconds. If you skip this step, ArgoCD will undo every subscription patch, DSC edit, ISVC conversion, ConfigMap change, and operator uninstall you perform in the following modules -often before you finish reading the verify block.

Disable auto-sync on every ArgoCD Application before touching anything else. Manual sync from the ArgoCD UI still works if you ever need it, but nothing will happen unattended.
====

[.console-input]
[source,role="execute"]
----
oc get applications.argoproj.io -A -o jsonpath='{range .items[*]}{.metadata.namespace} {.metadata.name}{"\n"}{end}' | \
  while read -r NS NAME; do
    oc -n "$NS" patch application.argoproj.io "$NAME" --type=merge \
      -p='{"spec":{"syncPolicy":{"automated":null}}}'
  done
----

[IMPORTANT]
====
*Clearing `syncPolicy.automated` is not enough on its own -you must also terminate any sync operation that is already in flight.*

An ArgoCD sync that started *before* you cleared the policy keeps running under its own `retry` block (these Applications ship with `retry.limit: 60` and a backoff up to 2m). Each retry re-applies the Git manifests, so it will happily undo your work *tens of minutes* after auto-sync is "disabled" -with `AUTOMATED` reading `<none>` the whole time.

On a freshly provisioned lab cluster this is not hypothetical: `rhoai-2254-sample-kserve-modelmesh` is routinely still syncing at this point. If you skip this, it re-applies the original ModelMesh `ServingRuntime` partway through Module 4 and re-introduces the `ModelMesh ServingRuntime` critical you already cleared in Module 3.

Run this immediately after the disable loop:

[.console-input]
[source,role="execute"]
----
oc get applications.argoproj.io -A -o json \
  | jq -r '.items[] | select(.operation != null) | "\(.metadata.namespace) \(.metadata.name)"' \
  | while read -r NS NAME; do
      echo "Terminating in-flight sync operation on $NAME"
      oc -n "$NS" patch application.argoproj.io "$NAME" --type=merge -p '{"operation":null}'
    done
----
====

=== Verify

Every row must show `<none>` in the `AUTOMATED` column, *and* no Application may still carry a running `operation`. If either check fails, re-run the corresponding loop before continuing:

[.console-input]
[source,role="execute"]
----
oc get applications.argoproj.io -A \
  -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,AUTOMATED:.spec.syncPolicy.automated'

oc get applications.argoproj.io -A -o json \
  | jq -r '.items[] | select(.operation != null) | "STILL SYNCING: \(.metadata.name)"'
echo "--- no Application should be listed as STILL SYNCING ---"
----

== The starting cluster

Your lab cluster was provisioned with OpenShift AI {source-version} in a realistic, messy pre-migration state. The DSC is `Ready` and the cluster is healthy -but it carries workloads that the 3.x removals would break:

* *Serverless model-serving ISVCs* in `ml-project-a` and `ml-project-b` -running on KServe Serverless mode, which 3.x removes
* *A ModelMesh model* in `ml-project-c` -multi-model serving, which 3.x removes entirely
* *A custom (BYON) workbench image* registered in the dashboard -built for the 2.x auth model
* *Sample workbenches and a Data Science Pipelines application*
* The 2.x serving stack: Service Mesh 2, OpenShift Serverless, and standalone Authorino

Your job is to carry all of it cleanly onto 3.5.

== What you'll do

[cols="1,3",options="header"]
|===
| Module | What you'll accomplish
| *Module 1: Test baseline* | Exercise every user-facing workload (inference calls, workbenches, pipelines, Ray jobs) and save a baseline snapshot so you can compare before vs after.
| *Module 2: Assess* | Run the `rhai-cli` assessment, read its findings, and learn why a clean lint is not a workload inventory.
| *Module 3: Convert serving* | Convert the Serverless ISVCs to RawDeployment and migrate the ModelMesh model to KServe -*before* the components that host them are removed.
| *Module 4: Remediate platform* | Flip the removed components to `Removed`, patch the model-serving ConfigMap, remove the Service Mesh dependency, and uninstall the 2.x operators.
| *Module 5: Workbench images* | Discover the custom workbench image, learn what a custom image needs to change for 3.x, re-register it to a rebuilt image, bump out-of-date tags, and stop every workbench.
| *Module 6: Upgrade* | Switch to the migration channel, drive the OLM upgrade to 3.5, then move to the stable channel.
| *Module 7: Verify* | Confirm the platform is healthy, the converted models still serve, the schema and HardwareProfiles migrated, and workbenches are patched onto the new auth model.
| *Module 8: Re-test* | Re-run every test from Module 1 against the migrated endpoints and diff against the baseline.
|===
