= Module 3: Convert the model-serving workloads
:source-highlighter: rouge
:toc: macro
:toclevels: 2

This is the heart of the migration. Your cluster runs four models: two on KServe Serverless mode, one on ModelMesh, and one already on KServe RawDeployment. The first three are the work -both Serverless and ModelMesh are removed in 3.x, and if you disable those components while the models still depend on them, the models stop serving. The RawDeployment model is already 3.x-compatible and you leave it alone.

So you convert *first*. In this module you'll convert both Serverless InferenceServices to RawDeployment with a single cluster-wide `rhai-cli migrate` action (backup-and-recreate under the hood, because the admission webhook blocks in-place mode edits), then migrate the ModelMesh model in place to a single-model KServe RawDeployment. Only after this is done -in Module 4 -will you disable the components.

== Learning objectives

By the end of this module, you'll be able to:

* Enumerate InferenceServices by deployment mode
* Convert every Serverless ISVC to RawDeployment cluster-wide with one non-interactive `rhai-cli migrate` action
* Migrate a ModelMesh model to a single-model KServe RawDeployment ISVC in place
* Recover a PVC-backed OVMS model that the ModelMesh conversion leaves crash-looping
* Verify every model is RawDeployment and `Ready` before touching the components

== Exercise 3.2: Convert the Serverless ISVCs

`modelserving.serverless-to-raw` is the official migrate action. In {target-version} it runs *cluster-wide and non-interactive* — a single invocation converts *every* Serverless ISVC in *all* namespaces at once. There is no per-namespace loop, no interactive model-selection prompt, and no resource-naming choice: each ISVC is converted to RawDeployment *in place*, keeping its original name (`my-serverless-isvc`, `another-sl-model`), and the authentication resources (ServiceAccount, Role, RoleBinding) are handled automatically. The KServe admission webhook rejects in-place `oc patch` of `deploymentMode`, so the action does a backup-and-recreate under the hood (manual fallback: https://access.redhat.com/articles/7134025).

[NOTE]
====
*Both conversion actions in this module prompt for confirmation before they change anything* (`About to convert N InferenceService(s) … Proceed with conversion? [y/N]`). That is why the commands are run with `oc exec -it` — enter `y` at the prompt.

The default is `N`, so a stray Enter *cancels*. If you see `User cancelled … conversion` followed by `completed with skipped steps`, nothing was changed — just re-run the command. The `--dry-run` invocations do not prompt.
====

Preview the conversion across all namespaces with `--dry-run` first:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -it -- \
  rhai-cli migrate run --migration modelserving.serverless-to-raw --target-version 3.5.0 --dry-run
----

Review the planned changes for every namespace. When it looks right, apply — re-run the same command without `--dry-run`:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -it -- \
  rhai-cli migrate run --migration modelserving.serverless-to-raw --target-version 3.5.0
----

The action removes the legacy Serverless ISVCs, their ServingRuntimes, and the associated auth/Istio resources, then applies the RawDeployment replacements — for both `ml-project-a` and `ml-project-b` in one shot.

== Exercise 3.4: Understand the ModelMesh model

ModelMesh is *multi-model serving* -one ServingRuntime hosts many models, keyed by a storage path. 3.x has no ModelMesh, so the model must be re-deployed as a *single-model* KServe RawDeployment ISVC backed by a single-model ServingRuntime.

Inspect the ModelMesh ISVC and its multi-model runtime:

[.console-input]
[source,role="execute"]
----
oc get isvc my-modelmesh-isvc -n ml-project-c -o json \
  | jq '.spec.predictor.model | {modelFormat, runtime, storage}'
echo "--- multi-model ServingRuntime ---"
oc get servingruntime ovms-mm -n ml-project-c -o jsonpath='multiModel={.spec.multiModel}{"\n"}'
----

[.console-output]
----
{
  "modelFormat": {
    "name": "onnx",
    "version": "1"
  },
  "runtime": "ovms-mm",
  "storage": {
    "key": "pvc-models",
    "path": "mobilenet"
  }
}
--- multi-model ServingRuntime ---
multiModel=true
----

This is a MobileNetV2 image classifier in *ONNX* format, served by OpenVINO Model Server (OVMS) in ModelMesh multi-model mode. The model lives on a PVC (`model-store`) under the OVMS layout `mobilenet/1/`. To migrate it you re-deploy the *same model* on a *single-model* OVMS ServingRuntime as a KServe RawDeployment ISVC, pointing `storageUri` at the same PVC path. ONNX is a first-class format for both ModelMesh OVMS and single-model KServe OVMS, so this is a true re-host -no model conversion, no data movement.

Confirm the model file is present on the PVC:

[.console-input]
[source,role="execute"]
----
oc -n ml-project-c get pvc model-store -o jsonpath='PVC: {.status.phase}{"\n"}'
----

=== Verify

[.console-input]
[source,role="execute"]
----
oc get servingruntime ovms-mm -n ml-project-c -o jsonpath='{.spec.multiModel}{"\n"}'
----

✓ Output is `true` -confirming this is a ModelMesh multi-model runtime

== Exercise 3.5: Re-host the model on KServe RawDeployment

`modelserving.modelmesh-to-raw` is the official migrate action. In {target-version} it runs *in place in a single namespace and non-interactive* — there is no cross-namespace source→target step, no runtime scale-to-zero dance, and no interactive model/template selection. It discovers the ModelMesh ISVCs, transforms each to a single-model RawDeployment ServingRuntime + ISVC keeping the original name, and (for a natively-supported format like ONNX/OpenVINO IR) selects the single-model `kserve-ovms` runtime automatically. Because it works in place, the old *scale-the-ModelMesh-runtime-to-zero to release an RWO PVC* step no longer applies.

Preview first with `--dry-run`, then run the conversion:

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -it -- \
  rhai-cli migrate run --migration modelserving.modelmesh-to-raw --target-version 3.5.0 --dry-run
----

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -it -- \
  rhai-cli migrate run --migration modelserving.modelmesh-to-raw --target-version 3.5.0
----

The action keeps the original name. The ISVC stays `my-modelmesh-isvc` -only `.status.deploymentMode` flips from `ModelMesh` to `RawDeployment`. Exercise 3.6 cleans up any leftover multi-model ServingRuntime.

[WARNING]
====
*A PVC-backed OVMS model is NOT fully migrated and will crash-loop — this is the lab's key troubleshooting exercise.*

Even though `modelserving.modelmesh-to-raw` reports `Migration completed successfully!`, this MobileNet model (PVC-backed OVMS) does *not* come up. The action migrates the ISVC/runtime *metadata* (sets `multiModel=false`, renames the container to `kserve-container`, drops the `modelmesh-enabled` namespace label) but does *not* rewrite three things, so the new RawDeployment predictor never becomes Ready. The symptoms appear in this order:

1. *Webhook rejects the pod* — `storage type must be one of [s3, hdfs, webhdfs]. storage type [pvc] is not supported` (the ModelMesh `storage: {key, path}` block was copied verbatim).
2. *OVMS crash-loops* — `Configuration file is invalid /models/model_config_list.json` (it kept the multi-model launch args).
3. *Pod runs but stays `0/1`* — the readiness probe never passes (no container port is declared, so KServe defaults the probe to `tcpSocket:8080`, but OVMS serves REST on 8888).

Apply all three fixes. Values for this lab: ISVC `my-modelmesh-isvc`, namespace `ml-project-c`, runtime `ovms-mm`, PVC `model-store`, model path `mobilenet` (resolve the PVC name from the ModelMesh `storage-config` secret's key if you adapt this to your own cluster):

[source,bash]
----
# 1. PVC storage → storageUri
oc patch isvc my-modelmesh-isvc -n ml-project-c --type=merge \
  -p '{"spec":{"predictor":{"model":{"storageUri":"pvc://model-store/mobilenet","storage":null}}}}'

# 2. OVMS multi-model args → single-model (serve one model from /mnt/models)
oc patch servingruntime ovms-mm -n ml-project-c --type=json -p '[{"op":"replace","path":"/spec/containers/0/args","value":[
  "--model_name=my-modelmesh-isvc","--model_path=/mnt/models","--port=8001","--rest_port=8888",
  "--file_system_poll_wait_seconds=0","--grpc_bind_address=0.0.0.0","--rest_bind_address=0.0.0.0"]}]'

# 3. Declare the container port + a readiness probe on the OVMS REST port (8888)
oc patch servingruntime ovms-mm -n ml-project-c --type=json -p '[
  {"op":"add","path":"/spec/containers/0/ports","value":[{"containerPort":8888,"protocol":"TCP"}]},
  {"op":"add","path":"/spec/containers/0/readinessProbe","value":{"tcpSocket":{"port":8888},"periodSeconds":10,"failureThreshold":3,"timeoutSeconds":5}}]'

oc rollout restart deployment my-modelmesh-isvc-predictor -n ml-project-c
----

`pvc://model-store/mobilenet` points at the OVMS-layout root; OVMS auto-discovers the `1/` version subdirectory. After the rollout the predictor should reach `1/1` and the ISVC `Ready=True`. Full manual workflow: https://access.redhat.com/articles/7134025.
====

=== Verify

Re-run until `READY=True`:

[.console-input]
[source,role="execute"]
----
oc get isvc my-modelmesh-isvc -n ml-project-c -o jsonpath='mode={.status.deploymentMode} ready={.status.conditions[?(@.type=="Ready")].status}{"\n"}'
----

[.console-output]
----

----

== Exercise 3.6: Remove the ModelMesh ISVC and runtime

Sweep for leftover ModelMesh resources. Because the in-place conversion keeps the original name and drops `multiModel`, both selectors typically return zero rows already (the ISVC was converted in place; the action removed the multi-model ServingRuntime). The sweep catches any leftovers all the same:

[.console-input]
[source,role="execute"]
----
oc get isvc -n ml-project-c -o json | jq -r '.items[]
  | select(.status.deploymentMode == "ModelMesh"
        or .metadata.annotations["serving.kserve.io/deploymentMode"] == "ModelMesh")

  | while read -r name; do echo "Deleting ModelMesh ISVC: $name"; oc delete isvc "$name" -n ml-project-c; done

  | select(.spec.multiModel==true)
  | .metadata.name' \
  | while read -r name; do echo "Deleting multi-model ServingRuntime: $name"; oc delete servingruntime "$name" -n ml-project-c; done
----

== Troubleshooting

*Issue*: `oc apply` of the recreated ISVC fails with a `deploymentMode` webhook error.

*Solution*: This shouldn't happen with the `rhai-cli migrate` actions — `modelserving.serverless-to-raw` creates the new RawDeployment ISVC as a fresh object, which the webhook accepts. The webhook only blocks *changing* mode on an existing object. If you took the manual fallback path (https://access.redhat.com/articles/7134025), confirm you flipped the annotation in your backup file and deleted the old ISVC before re-applying.

*Issue*: The recreated ISVC sits `READY=False` for several minutes.

*Solution*: RawDeployment pulls and loads the model fresh. Watch the predictor pod: `oc get pods -n <ns> -l serving.kserve.io/inferenceservice=<name>`. A CPU model can take a few minutes. Check pod logs if it never becomes ready.

*Issue*: You can't delete the multi-model ServingRuntime -"still in use".

*Solution*: Delete the ModelMesh ISVC first (Exercise 3.6). The runtime can only be removed once no ISVC references it.

*Issue*: `oc delete isvc` on a leftover Serverless ISVC hangs forever -it stays in `Terminating` and the delete never returns.

*Solution*: This is a finalizer deadlock, and it's exactly why this module converts (and deletes) every Serverless ISVC *before* Module 4 removes Serverless and Service Mesh. A Serverless ISVC carries a KServe finalizer whose cleanup deletes the Knative `Service` and Istio `VirtualService` it owns. If those components are already gone, the finalizer can't reach their APIs, errors out, and never clears -so the object is stuck. Recovery: if the operators are still installed, re-enable Serverless/Service Mesh, let the delete finish, then remove them in the right order. If they're already uninstalled, force-clear the finalizer and recreate the model as RawDeployment: `oc patch isvc <name> -n <ns> --type=merge -p '{"metadata":{"finalizers":null}}'` (this skips the real cleanup, so sweep for orphaned `ksvc`/`virtualservice` afterward). The rule: never disable a component while a workload still depends on it.
