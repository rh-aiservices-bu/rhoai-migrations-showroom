Congratulations -you've migrated a production-shaped Red Hat OpenShift AI {source-version} cluster to 3.5, carrying live model-serving and workbench workloads across a breaking platform change.

== What you accomplished

You ran the full assessment-driven migration on a cluster that wasn't a clean demo:

* *Captured a baseline* of every user-facing workload (model inference responses, workbench HTTP status, DSPA health, Ray cluster status) and saved it as an archive. This is what gave Module 8 a hard "before" reference to diff against.
* *Assessed* the cluster with `rhai-cli lint`, separated critical findings from warnings, and learned the assessment is not a workload inventory.
* *Converted the model-serving workloads* -the hard part: two Serverless ISVCs converted to RawDeployment with backup-and-recreate (the webhook blocks in-place edits), and a ModelMesh model migrated off multi-model serving -*before* disabling the components that hosted them.
* *Backed up every workload with persistent state* -RayCluster CRs (via the `rhai-cli migrate` backup action), TrustyAI metrics + storage + Guardrails otelExporter config, and the AI Pipelines pre-upgrade DSPA snapshot. The backups are what give you a recovery path if a component drops state during the upgrade. Llama Stack (now OGX) is the exception -its 2→3 transition has no compatible upgrade path, so it is archived for reference and deleted pre-upgrade.
* *Remediated the platform* -disabled the removed components in the correct order, tore down the Service Mesh v2 dependency including the lingering member roll, uninstalled the 2.x operators, and deleted the Maistra Istio CRDs those operators left behind so the 3.5 Gateway API could install its own.
* *Handled the workbenches* -discovered and retired an orphaned custom image, bumped out-of-date tags, and stopped every workbench.
* *Upgraded* through the `{migration-channel}` channel to 3.5, then moved to `{stable-channel}`.
* *Verified* the result -platform healthy, all four models still serving on RawDeployment (displayed as *Standard* in 3.5) through Gateway API (the three you migrated plus the one already on RawDeployment), schema and HardwareProfiles migrated, RayClusters migrated to KubeRay-only management, and KFTO PyTorchJobs / Feast / Model Registry / AI Pipelines / TrustyAI all confirmed working against their pre-upgrade state.
* *Returned the cluster to service* -patched the workbenches onto kube-rbac-proxy, cleared the legacy OAuth Routes and Secrets, repointed the custom workbench at its rebuilt Gateway-API image, restarted every workbench, and removed the orphaned ModelMesh runtime Deployment the retired controller abandoned.
* *Re-tested* every user-facing workload against the new Gateway URLs and diffed against the Module 1 baseline. The before/after archive pair is your evidence that the migration didn't silently break anything.

== Key takeaways

* *Sequencing is everything.* Migrate workloads off a component before you remove the component. Convert Serverless and ModelMesh models first; only then disable those serving modes. Get the order wrong and you lose a running model.
* *The webhook forces backup-and-recreate.* You cannot change an ISVC's deployment mode in place -back up the spec, delete, and recreate with the new annotation.
* *The assessment is not an inventory.* A clean lint means no incompatible workloads, not an empty cluster. Always inventory `oc get isvc -A`, ServingRuntimes, and workbench images directly.
* *Kueue must be `Removed` or `Unmanaged` before upgrade.* In 3.5 the supported end states are `Removed` (Kueue disabled) or `Unmanaged` (backed by an external Red Hat build of Kueue / RHBOK). `Managed` is accepted by OLM for backwards compatibility but *rejected at runtime* -and left `Managed` at upgrade time its admission webhook can reject Job creation cluster-wide. Resolve the state before the upgrade.
* *The assessment surfaces additions, not just removals.* Findings like `llamastack / config` are 3.x prerequisites that don't exist yet -archive and delete the LlamaStackDistribution *before* the upgrade or it stops at that critical finding.
* *Llama Stack is delete-and-replace, not upgrade.* Rebranded *OGX (Open GenAI Stack)* in 3.5, its 2.25 → 3.x transition changes the database (SQLite → PostgreSQL), the Vector API, and the Inference API. There is no migration path: delete every `LlamaStackDistribution` before the upgrade and deploy fresh `OGXServer` (v1beta1) CRs afterward *on a cluster whose catalog ships the OGX operator*. This lab's catalog does not -the `ogx` DSC component has no backing CRD here, and forcing it to `Managed` takes the whole DSC `Not Ready` (see Module 7 Exercise 7.7). Leave it `Removed` and treat the OGX rebuild as follow-on work.
* *Uninstalling an operator does not remove its CRDs -and the leftovers can break the next version.* OLM never garbage-collects CRDs. The Service Mesh 2 CRDs outlive their operator and make the OpenShift Gateway API controller refuse to install its own (`"Istio CRDs are managed by an unknown party"`), which cascades all the way to a `Not Ready` DSC. Clearing them *before* the upgrade, after checking they hold zero custom resources, is the difference between a clean cut-over and a post-upgrade recovery.
* *Stopping workloads for an upgrade is only half a plan.* Every workbench is stopped in Module 5 and nothing restarts them automatically. A migration isn't finished when the platform reports `Ready` -it's finished when users can log back into the things they had before.
* *Back up before you flip.* RayClusters, TrustyAI metrics + data, and AI Pipelines DSPAs all have to be captured *before* the destructive flips in Module 4 -especially Ray, because disabling the CodeFlare/Ray component disables the controller that owns the `raycluster.backup` action's logic. Order: backup → flip, never flip → backup.
* *Most non-core components survive untouched.* KFTO PyTorchJobs, Feast Feature Stores, Model Registry, and AI Pipelines all continue through the upgrade with no spec changes. They still need verification (and Model Registry needs user comms because the dashboard nav moves) but no migration work.
* *Both URLs and pods change, intentionally.* External URLs move from Routes to Gateway API, and the 3.x kserve controller rolls each predictor pod onto the newer runtime images (including a newer vLLM) -no separate maintenance window required. Capture the new URLs for downstream consumers and confirm every ISVC recovers to `Ready=True` on the new platform.

== What this workshop did not cover

In a production migration you would also:

* *Take a verified backup first* (etcd snapshot plus OADP) -the only rollback path for an in-place migration.
* *Rebuild custom workbench images* for kube-rbac-proxy and Gateway API path routing -an application-owner task this lab only identified.
* *Plan the maintenance window* around stopping workbenches and the brief model-endpoint gap during the routing transition.
* *Notify downstream consumers* of the new model endpoint URLs before the window.
