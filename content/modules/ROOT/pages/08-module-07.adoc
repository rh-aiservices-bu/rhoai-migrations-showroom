= Module 7: Post-upgrade verification
:source-highlighter: rouge
:toc: macro
:toclevels: 2

The operator is on {target-version} and the DSC is `Ready`, but the migration isn't finished. The 3.x reconciler needs a few `rhai-cli migrate run` actions to bring components fully across (ConfigMap state, workbench auth, RayCluster CRs, GuardrailsOrchestrator schema, TrustyAI data). This module runs those actions and then sweeps every workload to confirm they survived the upgrade.

== Learning objectives

By the end of this module, you'll be able to:

* Confirm the operator, DSC, and DSCI are healthy on {target-version} and the Data Science Gateway is `Programmed`
* Run the required post-upgrade `rhai-cli migrate run` actions (ConfigMap, workbenches, Ray, GuardrailsOrchestrator)
* Recover the Data Science Gateway when leftover Service Mesh 2 Istio CRDs block it
* Verify every workload on the cluster is healthy and the rhai-cli lint is clean

The **Data Science Gateway must be `Programmed=True`** -the dashboard, model endpoints, and Model Registry all resolve through it. If it isn't, work through the Service Mesh 2 leftover-CRD recovery in Exercise 7.2 *before* verifying any component.

[NOTE]
====
*What the operator handles automatically.* Several tasks that were manual admin steps in earlier releases are now done by the {target-version} operator on startup -do *not* attempt them by hand:

* *HardwareProfile migration* -AcceleratorProfiles are converted to HardwareProfiles and Notebooks/InferenceServices are annotated (create-only; your customizations are preserved).

* *Kueue ValidatingAdmissionPolicyBinding cleanup* -deprecated pre-v2.29 resources are removed.
* *DSC v1→v2 API conversion* -via the conversion webhook, `datasciencepipelines` becomes `aipipelines` and the retired `modelmeshserving` and `codeflare` components are removed.
====

== Exercise 7.2: Recover the Data Science Gateway (leftover Service Mesh 2 Istio CRDs)

[IMPORTANT]
====
This is the *most common* reason a {target-version} upgrade lands with the DSC `Not Ready`. If Exercise 7.1 showed the gateway `Programmed=True`, skip to Exercise 7.3. If it showed `Programmed=False` (or empty), work through this exercise now -every component below depends on the gateway.
====

Uninstalling the Service Mesh 2 (Maistra 2.6.17) operator in Module 6 removed the *operator*, but *OLM never removes CRDs*, so the old `*.istio.io` CRDs (serving only `v1beta1`/`v1alpha3`) stay behind. On OCP 4.20.31+/4.21.22+/4.22+, Service Mesh 3 is *not required* -the OCP built-in Gateway API ("sail" Istio) provides the control plane, and it *refuses to install its own `v1` CRDs while foreign Istio CRDs exist*. The result is a gateway that never programs.

*Symptoms* (a self-reinforcing chain):

* DSC stuck `Not Ready`: `ProvisioningFailed: modelregistry`.
* `GatewayConfig/default-gateway`: `failed to lookup … DestinationRule in version "networking.istio.io/v1"`.
* `Gateway/data-science-gateway` (openshift-ingress): `Programmed=False`, listener `Bad TLS configuration`.
* `istiod-openshift-gateway` pod stuck *0/1*; log: `failed to list *v1.VirtualService: the server could not find the requested resource`.
* ModelRegistry: `failed to compute gateway domain: gateway domain is missing`.
* ingress-operator log: `"Istio CRDs are managed by an unknown party"` -the smoking gun (sail refusing to overwrite the SM2 CRDs).

First confirm *zero Istio custom resources* exist on-cluster (so deleting the CRDs loses no data) and that the leftover CRDs are Maistra 2.6.17:

[.console-input]
[source,role="execute"]
----
oc get crd -l maistra-version -o custom-columns=NAME:.metadata.name,VER:.metadata.labels.maistra-version
----

Then delete the ~14 stale `*.istio.io` CRDs (networking/security/telemetry/extensions) and restart the ingress-operator so the OCP sail controller reinstalls them at `v1`:

[.console-input]
[source,role="execute"]
----
oc delete crd destinationrules.networking.istio.io virtualservices.networking.istio.io \
  gateways.networking.istio.io serviceentries.networking.istio.io sidecars.networking.istio.io \
  envoyfilters.networking.istio.io workloadentries.networking.istio.io workloadgroups.networking.istio.io \
  proxyconfigs.networking.istio.io authorizationpolicies.security.istio.io \
  peerauthentications.security.istio.io requestauthentications.security.istio.io \
  telemetries.telemetry.istio.io wasmplugins.extensions.istio.io

oc rollout restart deploy/ingress-operator -n openshift-ingress-operator
----

The recovery *cascades and self-heals* after the restart: the `DestinationRule` CRD reappears serving `v1` → `istiod-openshift-gateway` goes *1/1* → `Gateway/data-science-gateway` *Programmed=True* → `GatewayConfig/default-gateway` *Ready* (domain assigned) → *ModelRegistry Ready* → *DSC Ready*.

=== Verify

[.console-input]
[source,role="execute"]
----
oc get gateway data-science-gateway -n openshift-ingress -o custom-columns='NAME:.metadata.name,PROGRAMMED:.status.conditions[?(@.type=="Programmed")].status'
oc get dsc default-dsc -o jsonpath='DSC: {.status.phase}{"\n"}'
----

✓ The Gateway reports `Programmed=True` and the DSC returns to `Ready`

[NOTE]
====
The `*.maistra.io` CRDs (servicemeshcontrolplanes, federation, etc.) hold 0 CRs and do *not* block the sail controller -they are harmless leftovers you can optionally remove too. This cleanup should have happened pre-upgrade in Module 4 Exercise 4.11 (`oc delete crd -l maistra-version`); doing it now is the recovery path.
====

== Exercise 7.3: Restore the inferenceservice-config ConfigMap

In Module 4 you marked `inferenceservice-config` as `managed=false` so the upgrade couldn't redeploy your ISVCs. With the operator on {target-version}, hand control back. The `modelserving.managed-isvc-config` migrate action restores the annotation, restarts the KServe controller, and verifies that no ISVC was silently redeployed.

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  /opt/rhai-cli/bin/rhai-cli migrate run \
  --migration modelserving.managed-isvc-config --target-version {target-version}.0
----

=== Verify

Confirm the ConfigMap is back under management, then confirm each ISVC came back `Ready` and reporting its deployment mode as `Standard` (in {target-version}, `RawDeployment` was renamed to *`Standard`*):

[.console-input]
[source,role="execute"]
----
oc get configmap inferenceservice-config -n redhat-ods-applications \
  -o jsonpath='managed={.metadata.annotations.opendatahub\.io/managed}{"\n"}'
oc get isvc -A -o json | jq -r '["NAMESPACE","NAME","DEPLOYMENT_MODE","READY"], (.items[] | [.metadata.namespace, .metadata.name, .status.deploymentMode, (.status.conditions[] | select(.type=="Ready") | .status)]) | @tsv' | column -t
----

✓ Output is `managed=true` and every ISVC shows `DEPLOYMENT_MODE = Standard` with `READY = True`

== Exercise 7.4: Patch the workbenches onto the new auth model

Workbenches still carry 2.x oauth-proxy configuration. Under 3.x they need kube-rbac-proxy or they hit redirect loops on first start. The `workbenches.patch-auth-model` migrate action patches each stopped workbench in place. It *prompts for confirmation twice* (once before patching, once before the OAuth cleanup) -enter `y` each time. A benign `phase pre-upgrade but effective phase is post-upgrade` warning may appear; ignore it.

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -it -- \
  /opt/rhai-cli/bin/rhai-cli migrate run \
  --migration workbenches.patch-auth-model --target-version {target-version}.0 \
  --only-stopped --with-cleanup
----

=== Verify

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  /opt/rhai-cli/bin/rhai-cli migrate run \
  --migration workbenches.verify-migration --target-version {target-version}.0
----

✓ Output reports `Legacy (2.x): 0` and `All workbenches have been migrated`

[NOTE]
====
Custom workbench images that bake in oauth-proxy can't be fixed by this patch -they need an image rebuild against kube-rbac-proxy. The action flags them; the rebuild is an application-owner task.
====

== Exercise 7.5: Migrate the RayClusters to KubeRay

The CodeFlare operator is gone; KubeRay manages Ray clusters directly. This step has a *Gateway API prerequisite* -confirm the Data Science Gateway is `Programmed=True` (Exercise 7.1/7.2) before running it. Preview with `--dry-run` (it replaces the old `list` subcommand), then apply (your pre-upgrade backups from Module 4 Exercise 4.1 are your safety net if anything breaks):

[.console-input]
[source,role="execute"]
----
oc exec -n rhai-migration rhai-cli-0 -- \
  /opt/rhai-cli/bin/rhai-cli migrate run \
  --migration raycluster.migrate --target-version {target-version}.0 --dry-run

oc exec -n rhai-migration rhai-cli-0 -- \
  /opt/rhai-cli/bin/rhai-cli migrate run \
  --migration raycluster.migrate --target-version {target-version}.0
----

The action migrates all clusters at once; scope to one with `--raycluster-cluster` / `--raycluster-namespace`, or recreate from a backup with `--raycluster-from-backup`. Each migrated cluster restarts its head + worker pods.

=== Verify

[.console-input]
[source,role="execute"]
----
oc get raycluster -A
----

✓ Every RayCluster reports `Status=ready` with workers available

== Troubleshooting

*Issue*: A model returns `Ready=False` after the upgrade.

*Solution*: Confirm Exercise 7.3 (ConfigMap restore) was applied before model verification. If the issue persists, check the predictor pod's `events` and `logs` (`oc get events -n <ns>`, `oc logs <pod>`).

*Issue*: The Gateway dashboard URL doesn't resolve, but the `data-science-gateway` Gateway shows `PROGRAMMED=True`.

*Solution*: On clusters with an SRE-managed admission webhook restricting NetworkPolicy creation in `openshift-*` namespaces, the GatewayConfig reconciler's NetworkPolicy POST is rejected: `oc patch gatewayconfig default-gateway --type=merge -p '{"spec":{"networkPolicy":{"ingress":{"enabled":false}}}}'`.

*Issue*: The dashboard URL is unreachable and the `data-science-gateway` Gateway shows `PROGRAMMED=False`, with `no matches for kind "DestinationRule" in version networking.istio.io/v1` and `istiod-openshift-gateway` stuck `0/1`.

*Solution*: This is the leftover Service Mesh 2 Istio CRD problem -see *Exercise 7.2* for the full diagnosis and recovery (`oc delete crd -l maistra-version` then restart the ingress-operator).

*Issue*: `openshift-gateway` is in `ReconcileError` with `validation error: version "v1.26.2" is end-of-life and cannot be installed`.

*Solution*: The Service Mesh Operator 3 was upgraded to 3.4.0, which rejects the `v1.26.2` Istio version that OCP 4.19–4.21's ingress operator hardcodes for the Gateway API. Editing the version by hand is reverted within seconds. There is no supported OSSM downgrade — prevention is the only clean path, so this InstallPlan should never have been approved (see the WARNING in Module 6, Exercise 6.3). A cluster already on OSSM 3.4.0 is a restore-from-backup case; do not attempt informal downgrade workarounds. Track link:https://redhat.atlassian.net/browse/OSSM-14917[OSSM-14917^] / link:https://redhat.atlassian.net/browse/OCPBUGS-92038[OCPBUGS-92038^].

*Issue*: `workbenches.verify-migration` reports `Failed: N`.

*Solution*: Inspect each with `oc describe notebook <name> -n <ns>`. The most common cause is a custom workbench image that still embeds oauth-proxy and must be rebuilt for kube-rbac-proxy.
